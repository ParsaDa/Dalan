# Dalan — handoff

Written 2026-11-15, updated 2026-11-19 for 0.5.3, for whoever continues this work (a person or a coding agent). Read this first, then `CLAUDE.md` (upstream's rules, all still binding), `dalan/UPSTREAM.md`, `dalan/TUNNELS.md` and `dalan/TOR.md`.

## What Dalan is

A fork of [3x-ui](https://github.com/MHSanaei/3x-ui) (`ParsaDa/dalan`, GPL-3.0, open source) that adds managed tunnels between servers. Owner: Parsa (`ParsaDa`). He works in Persian; write to him in Persian, plainly, without assuming deep Go knowledge.

Why it exists: during internet shutdowns in Iran only connections opened from outside toward Iran survive. Existing panels do not manage tunnels, so operators wire them by hand with separate scripts on both servers.

### What 0.5.2 adds (merged as PR #17, released as `v0.5.2`)

- **Engines on a fresh install**: `x-ui install-engines` (`engines_cmd.go`, `internal/web/service/engine_preinstall.go`) puts BackPack, Rakhsh and Tor in place at their pinned versions, each with its own 2-minute limit; the hook in `install.sh` is generated by `scripts/dalan/rebrand.sh` and never fails the install. A missing engine is only reported ("Some engines were not installed (...)"). `XUI_ENGINE_PROXY` sends those downloads through a proxy address or share link.
- **Download route** (`internal/web/service/engine_route.go`): `EngineRoute{via, value}` with `panel`, `direct`, `outbound` (tag of an outbound of the running core, tunnels and Tor exits included) and `link` (socks5/http address, or a share link run in a short-lived core by `OutboundService.OpenProxy`). `TunnelService.InstallEngine/UpdateEngine` and `TorService.InstallEngine` take the route; `GET /panel/api/tunnels/engine/routes` lists the choices. UI: `components/engine/EngineRoutePicker.tsx` in the engine bar and the Tor window (hidden when a node does the download). Operator text: "Download route" in `dalan/TUNNELS.md`.
- Not done on purpose: a route for engine downloads that a node serves to its main panel (the node still uses its own panel setting), saving a route, packet-loss switching, a fourth engine.

### What 0.5.1 adds (merged as PR #16, released as `v0.5.1`)

- **Tor exits by country**, run on the panel server itself (`internal/tor/`, `internal/web/service/tor.go`, `internal/web/controller/tor.go`, model `TorExit`). One managed Tor per enabled country (`ExitNodes {cc}`, `StrictNodes 1`, loopback SOCKS5 on 62700-62789, at most 10 enabled), injected into the Xray config as outbound `tor-<cc>` and shown in Outbounds with a status chip (connected only after a real request through it). Install = Tor Expert Bundle 16.0.1, checksummed; global `torBridges` setting (obfs4, snowflake, webtunnel, meek_lite). A throwaway Tor tests a country (`Trial`, one at a time, 90 s). Operator guide: `dalan/TOR.md`.
- **Panel**: the Tor window (`pages/xray/overrides/TorModal.tsx`, opened from the Outbounds menu): every assigned ISO country with flag and English name only, Test/Add/Remove, engine install card, bridges under Advanced. `GET/POST /panel/api/tor/*`.
- Not done on purpose: a rollback button (the API exists), UDP (Tor is TCP only), packet-loss switching, a fourth engine.

### What 0.5.0 adds

- **Rakhsh** (`CluvexStudio/rakhsh`, AGPL Rust core, run as its own unmodified binary like BackPack). Engine id `rakhsh`; `internal/tunnel/rakhsh/` has `RenderConfig`, `Catalog`/`ValidateOptions` (options.go), `Supervisor` (a thin `engine.Supervisor`, shared with BackPack in `internal/tunnel/engine/`), `Install` (pinned `v0.1.0`, verified against the release checksums), `GenerateKeyPair`/`BridgeSecret` (X25519 keys; the bridge key is derived from the portal's and the tunnel UUID) and `ReadStatus` (`rakhsh status --socket S --json`: lanes up, loss, latency).
- **Setup link version 4** carries `rakhshSecret`/`rakhshPeer`; the link is a secret. `ServerTunnel` gained `rakhsh_secret` and `rakhsh_peer_public` (plain string columns, added by AutoMigrate like the BackPack ones; no hand-written migration was needed).
- **Per-engine install, update, release** in `tunnel_engine.go` (`externalEngine` table); `POST .../engine/install|update|release` and `GET .../options|engine` take `engine` (default `backpack`, so old clients keep working). `TunnelService.ReconcileEngines`/`StopEngines` run both external engines; `checkLinkAddressesFree` refuses a link address that another tunnel already listens on.
- **Panel**: Rakhsh in the engine picker, carriers, forwards (`listen=target[/udp]`), a links field (carrier, address, per-link overrides), every catalog option filtered by role and mode, raw carriers warn and require `peer_ip`, one install/update bar per engine (`TunnelEngineBar.tsx`), lanes and loss in the status cell. `GET /panel/api/tunnels/options?engine=` serves the catalog.
- Not done on purpose: loss-aware carrier switching (the owner wants to talk about it later), Rakhsh's router sections, a fourth engine.

### What 0.4.5 adds

- **Reverse / direct label** on every tunnel (`ServerTunnel.Mode`, empty reads as reverse) in the Tunnels page and the outbounds table.
- **Direct layer-3 tunnels** (BackPack `[l3]`): `backpack.renderDirect`, link version 3 (`tunnel.setupLinkBackpackOptions`) mirrors the `local_ip`/`peer_ip` pair for the exit end; `listensOnPort` decides which end opens its port (the exit end of a direct tunnel); status is the link interface `dl<id>` (`TunnelService.directStatus`); no relay port, so it is never an Xray outbound (`tunnelroute.Routable`).
- **All reverse options of BackPack 1.9.0**: `backpack.Catalog` (`internal/tunnel/backpack/options.go`), served by `GET /panel/api/tunnels/options`, validated by `ValidateOptions`/`RenderConfig`, stored in `ServerTunnel.Options`, shown by `TunnelOptionFields.tsx`. Pin moved to `v1.9.0`.
- **Edit in place**: `TunnelService.Update` (`tunnel_edit.go`), `POST /panel/api/tunnels/update/:id`; an entry end made for a node pushes the new link first (`pushToNode`); `Import` of a link whose name is already a dialing end updates it (`updateDialingEnd`).
- **Live traffic**: the websocket `outbounds` push also patches the tunnels query (`withLiveTraffic`); **tunnels in the Outbounds table** (read-only rows, no separate tunnel list there).

### What 0.4.0 adds (PR #13)

- **Tunnels as Xray outbounds.** An entry tunnel is the outbound `tunnel-<name>`; an inbound or routing rule can choose it. A management tunnel (`ManagePort > 0`) is never offered. `tunnelroute.Routable` says which tunnels count.
- **Node management over the existing tunnel**, BackPack engine log lines in the panel log, per-tunnel traffic totals (Apply switches outbound stats on for entry tunnels in the generated config).
- **One-panel tunnel creation**: *New tunnel → Create the other end on a node*; enrolling a node can also create its data tunnel (`withTunnel`, default on); deleting removes both ends, with "remove this end only" when the node is unreachable. `refuseWhileInUse` stops deleting a tunnel a pool or a node still uses.
- **Spare tunnels**: `internal/tunnel/pool` (pure decision: three checks in a row, at least 50 ms and 30% faster, or the tunnel in use is down), `internal/tunnel/tunnelroute/pool.go` (balancer `pool-<name>`, `ApplyPools`), `TunnelPoolService`, job `tunnel_pool_job.go` every 15 s, hot switch through `XrayService.OverrideBalancer`.
- **Route test**: `internal/tunnel/dial.go`, `Remote.DialPorts`, `TunnelService.RouteTest` — this server listens, the node dials, a port counts only if the connection arrived here.
- **Engine delivery and update**: `backpack.Fetch/Place/Rollback/LatestVersion`, `TunnelService.UpdateEngine` (rolls back when connected tunnels do not return within 75 s), the node serves a release in 512 KiB parts (`EngineReleaseChunk`, `Remote.FetchEngineRelease`) because every node call has a 10 s limit. A stopped engine's status file is deleted so it cannot read as connected.
- **Install and enrol in one command**: the enrolment dialog shows `XUI_ENROL='<link>' bash <(curl … install.sh)`. The hook in `install.sh` is added by `scripts/dalan/rebrand.sh` (`add_enrol_on_install`) so upstream syncs keep it.
- **Container**: `internal/frontdoor` (path routing from the panel's own inbounds/settings, `FlushInterval -1` for XHTTP, upgrades pass), `service.FrontDoorService`, `DockerPrepare.sh` (PORT → `DALAN_FRONT_PORT`, panel to `XUI_PORT=20530`, `DALAN_ADMIN_*`, one-time `DALAN_ENROL`). Guide: `dalan/CONTAINER.md`.

### Where the tunnel code is

- `internal/database/model/server_tunnel.go` — `ServerTunnel`, one end of a tunnel. Roles `portal` (entry, listens) and `bridge` (exit, dials). Engines `xray`, `backpack`, `rakhsh`.
- `internal/tunnel/setup.go` — `NewPortal`, `SetupLink`, `ParseSetupLink`. Link format `dalan://tunnel/<base64url JSON>`; version 2 = BackPack, version 3 = BackPack with options or direct mode, version 4 = Rakhsh; a version 1 (Xray) link is refused. A Rakhsh link leaves `bind` out because it names an address of one server.
- `internal/tunnel/tunnelroute/apply.go` — injects the relay outbound/inbound and routing rules of enabled BackPack and Rakhsh entry tunnels into the *generated* Xray config (never the stored template); `pool.go` holds the spare-tunnel balancers. It replaced `xrayreverse`, whose Xray portal/bridge/probe/management inbounds were removed in 0.6.0.
- `internal/tunnel/probe.go` — one GET through a SOCKS address (`ProbeVia`); reports latency, exit IP and country (Cloudflare trace). Tor exits use it; tunnels report their own engine status.
- `internal/tunnel/rakhsh/` — see "What 0.5.0 adds"; the engine-neutral supervisor, installer and management forward live in `internal/tunnel/engine/`.
- `internal/tunnel/backpack/` — `RenderConfig` (TOML), `Supervisor` (one process per tunnel, restart on change or crash, config file 0600 and removed with the tunnel), `ReadSnapshot` (`<name>.metrics.json`), `Install` (pinned `v1.9.0`, verified against the release's `SHA256SUMS`), `Catalog`/`ValidateOptions` (options.go), `renderDirect` and `DirectInterface` (config.go).
- `ServerTunnel.ManagePort` marks a management tunnel (a rider with `ParentId` = its parent tunnel). `engine.WithManagement` adds the loopback forward `127.0.0.1:<ManagePort>=127.0.0.1:<ManageTarget>` to the parent's forwarded ports, so the node's panel is reachable through the tunnel. `internal/web/service/tunnel_management.go` creates and deletes riders; the ordinary tunnel routes refuse to delete or test them.
- `internal/tunnel/enrol/` — the enrolment link (`dalan://enrol/...`), the sealed request and reply (X25519 + HKDF + AES-GCM, key in the link) and the node's HTTP client.
- `internal/web/service/enrolment/` — `Create`, `Redeem`, `Delete`, `NodeDeleted` on the main panel and `Join` on the node. It is its own package because `service/panel` imports `service`. `internal/database/model/node_enrolment.go` is its table. Routes in `internal/web/controller/enrolment.go`: `/panel/api/enrolments/*` and the public `POST <base path>dalan/enrol`. CLI: `enrol_cmd.go` (`x-ui enrol <link>`); `x-ui.sh` gets its `enrol` case from `scripts/dalan/rebrand.sh` and restarts the service afterwards. Enrolment now creates the node's own BackPack/Rakhsh tunnel `<name>` plus rider `node-<name>`, link version 2 grants only that tunnel (`Grant.DataTunnel`), and `NeedsReenrol` flags nodes whose Xray tunnel the `migrateRemoveXrayTunnels` migration removed (their node record is kept and re-pointed by `storeNode`). Design: `dalan/plans/2026-11-20-node-link-on-engines-design.md`.
- `frontend/src/pages/nodes/EnrolNode.tsx`, `frontend/src/api/queries/useEnrolments.ts`, tests in `frontend/src/test/enrol-node.test.tsx`.
- `internal/web/service/tunnel.go`, `internal/web/controller/tunnel.go` — service and routes. The hook into config generation is one block in `XrayService.GetXrayConfig` (`internal/web/service/xray.go`); BackPack engines start in `startTask` and stop in the stop path of `internal/web/web.go`.
- `frontend/src/pages/tunnels/TunnelsPage.tsx`, `frontend/src/api/queries/useTunnels.ts`, tests in `frontend/src/test/tunnels-page.test.tsx`.
- Engine files at runtime: binary `<bin folder>/backpack` (normally `/usr/local/x-ui/bin/backpack`), configs and status in `<db folder>/tunnels/` (normally `/etc/x-ui/tunnels/`).

Every place Dalan touches upstream code is listed in `dalan/UPSTREAM.md`. Keep that table current; new features go in new files and packages.

## Known gaps and rough edges

- Translations: only English and Persian are translated; the other 12 locale files carry the English text for every `pages.tunnels.*` key.
- The panel still shows the 3x-ui version number (3.11.0) as its version; Dalan's version appears only in the update dialog.
- Traffic totals are shown for entry tunnels that are Xray outbounds; direct tunnels show none.
- BackPack: forwarded-port conflicts with local inbounds are not checked; `skip_optz` is left at the engine default, so BackPack applies its own TCP tuning to the host.
- Deleting a tunnel on one server leaves the other end in place. The same holds for an enrolled node: deleting it on the main panel leaves the bridge `node-<name>` and the main panel's API token on the node.
- Enrolment: a node whose panel listens on one specific IP is refused (the bridge delivers to 127.0.0.1); each node takes its own tunnel port on the main panel; an https node is registered with certificate verification off, because the hop is loopback through the tunnel; a management tunnel has no status of its own in the Tunnels page (the node's status is its health); a Join that imports the data tunnel after the management tunnel has no rollback; joining a second main panel with the same data-tunnel name clashes.
- `docs/content/docs/en/reference/api/meta.json` lists neither `tunnels` nor `node-enrolment`, so those generated pages are not in the docs site navigation.
- A data race inside xray-core's VLESS reverse monitor (`proxy/vless/outbound`, handler read while `New` is still writing it) makes the two-core traffic test unusable under `-race`; the file carries `//go:build !race`. Worth reporting upstream.
- `node-e2e` in CI failed once with `bind: address already in use` in upstream's harness and passed on re-run. Treat one such failure as a flake, a second as real.

## How to work in this repo

- Follow `CLAUDE.md`: TDD with tests that can fail, comments ≤ 2 lines, conventional commits with a body, one focused diff per PR.
- A new route needs, in the same PR: an entry in `frontend/src/pages/api-docs/endpoints.ts`, `make gen`, copy `frontend/public/openapi.json` to `docs/public/openapi.json`, and `cd docs && pnpm gen:api`. A new struct in a response needs `StructAllow` in `tools/openapigen/main.go`.
- A new i18n key goes in all 14 files under `internal/web/translation/` and must be used in the same commit (`frontend/src/test/i18n-dead-keys.test.ts`).
- A new model goes in both `internal/database/db.go` (AutoMigrate list) and `internal/database/migrate_data.go` (`migrationModels`).
- Go imports: standard library, third party, then this module, each as its own group (goimports with a local prefix). Requests need a context (`noctx`), including `exec.CommandContext`.
- Local gate: `make verify` (needs Go 1.27, Node 26, `npm ci` in `frontend/`, Playwright Chromium). CI additionally runs `make race`, `make vulncheck`, live Postgres and `make node-e2e`.
- `make brand-check` must stay green. Never hand-edit a URL in a root `*.sh` file; change `scripts/dalan/rebrand.sh` and re-run it.
- Upstream updates: `bash scripts/dalan/sync-upstream.sh`, then `make verify`. See `dalan/UPSTREAM.md`.

## Releasing

1. Create the release on GitHub with a new tag `vX.Y.Z` on `main`, marked latest. `release.yml` writes the tag into `internal/config/dalan_version` before it builds, so the binary reports the tag it was released as (the Docker image gets the same through the `DALAN_TAG` build argument); the file in the repo does not need to move first.
2. `release.yml` uploads the build to that release as a pre-release upload; afterwards confirm the release is still marked **Latest**. The installer and the in-panel update only see the latest release.
3. A tag must be exactly `vX.Y.Z`; the build fails on anything else, e.g. `v1.2.3-rc1`.
